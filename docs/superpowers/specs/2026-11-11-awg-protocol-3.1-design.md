# Протокол AmneziaWG 3.1 в awg-vps-kit: дизайн

Дата: 2026-11-11. Согласовано с пользователем: целевой уровень — 3.1 (без отдельного 3.0).

## Цель

Дать серверам кита opt-in уровень протокола AmneziaWG 3.1: шифрование заголовков
(`HeaderProtectionKey`), паддинг содержимого (`ContentPaddingAddition`), таймеры-диапазоны
и `RandomTrailers` — самый сильный профиль против DPI. Основание: движок уже 3.1
(`upstream.lock`: amneziawg-go `b5928ef` = v3.1.20260828, amneziawg-tools `ee0f0a9` =
v3.1.20260812), а кит генерит только 1.0/1.5/2.0; клиентские поля 3.x в конфиги не
попадают, `awg-client protocol 3.0` отвергается.

## Подходы

- Только 3.0 (как просили изначально): отклонено. Клиенты с поддержкой только 3.0 — узкое
  окно (Amnezia VPN 5.0.0.2, ~август 2026); кто не обновился до 3.1, тому достаточно 2.0.
- **Выбрано: один новый уровень 3.1** с полным набором полей 3.x. Движок уже 3.1,
  `RandomTrailers` добавляется почти бесплатно, матрица переключений и тестов растёт на
  одну колонку, а не на две.
- Оба уровня 3.0 и 3.1: отклонено — вдвое больше пар переключений и наборов полей ради
  месячного окна совместимости.

## Ограничения

- Pure Bash, `set -euo pipefail`, Debian/Ubuntu, userspace `amneziawg-go`.
- `upstream.lock` не меняется: пины уже 3.1.
- Существующие серверы не трогаем: 3.1 — opt-in (`install.sh --protocol 3.1` или
  `awg-client protocol 3.1`), `update.sh` протокол не меняет (как сегодня).
- Формат `awg0.conf` (`[Peer]` + `# <name>` + `AllowedIPs = x/32`) и парсер `awg-client`
  остаются совместимыми.
- Поведение и генераторы 1.0/1.5/2.0 не меняются: `S3 = 8-64`, `S4 = 4-32` для 2.0
  остаются как есть.
- `Jc/Jmin/Jmax` остаются 5/40/900 (рандомизация — отдельный пункт `TODO.md`).
- Действующие серверы (EE/US/KZ/TR) переводятся на 3.1 только вручную и по отдельному
  решению; клиенты после переключения обязаны перекачать конфиги.
- Серверы, чьи конфиги используются контейнером AmneziaWG-to-Proxy, на 3.1 не
  переводятся до обновления движка в образе контейнера (см. раздел совместимости).

## Параметры уровня 3.1

Сервер `awg0.conf` (добавляется к существующим `Jc/Jmin/Jmax`):

| Поле | Значение | Основание |
|---|---|---|
| `S1 = S2 = S3 = S4` | одно случайное 15–32, четыре равных | при `RandomTrailers` docs.amnezia.org рекомендует равные S; ≥12 обязательно (nonce ChaCha20), иначе `EINVAL`; S4 держим небольшим — он ест MTU каждого пакета |
| `H1..H4` | `1/2/3/4` | рекомендация docs.amnezia.org при HPK: тип пакета скрывает Header Protection |
| `HeaderProtectionKey` | вывод `awg genkey` в момент установки/переключения | README AWG; секрет, `awg0.conf` уже 600 |
| `RandomTrailers` | `on` | 3.1; должен совпадать с клиентами |
| `ContentPaddingAddition` | `10-100` | upstream README советует на обеих сторонах: без поля на сервере трафик сервер→клиент остаётся без паддинга; совпадать не обязано |
| `DisableCookies` | на сервере не пишем (= off) | [решение кита] сервер сохраняет DoS-защиту WireGuard |

Клиентские конфиги 3.1: те же `S1-S4`, `H1-H4`, плюс:

| Поле | Значение | Комментарий |
|---|---|---|
| `HeaderProtectionKey` | копия серверного | обязательное совпадение |
| `RandomTrailers` | `on` | обязательное совпадение |
| `DisableCookies` | `on` | [решение кита] дефолт amnezia-client, поведение локальное |
| `I1`–`I5` | как для 1.5 (экспорт из `protocol`) | sender-поля, совпадать не обязаны |
| `ContentPaddingAddition` | `10-100` | дефолт amnezia-client 5.0.3.0, sender-поле |
| таймеры-диапазоны | `RekeyAfterTime = 100-120`, `RekeyTimeout = 3-7`, `RejectAfterTime = 150-180`, `KeepaliveTimeout = 5-15`, `MaxHandshakeAttempts = 15-20` | дефолты amnezia-client, client-side |
| `MTU` | по умолчанию **1280** для 3.1 | трейлеры и паддинг удлиняют пакеты: 1420 + ~100 байт паддинга > 1500 → фрагментация; MSS clamp 1240 уже стоит. Явный `$DIR/client-mtu` (`awg-client mtu`) перекрывает; для 1.0–2.0 дефолт остаётся 1420 |

Клиентские sender-поля (`ContentPaddingAddition`, таймеры, `DisableCookies`, `I1`–`I5`)
хранятся в `$DIR/protocol` по образцу `I1`: генерятся при установке/переключении на 3.1,
доступны для ручной правки, переживают переключения, экспортируются только на 3.1.
Серверное значение `ContentPaddingAddition` пишется в `awg0.conf` и не зависит от
клиентского. `PersistentKeepalive = 25` в `[Peer]` не меняется.

## Переключения протокола

- Любое `X → 3.1` и `3.1 → X`: полный путь как у 2.0 сегодня — бэкапы, перезапись полей,
  рестарт, откат файлов и протокола при неудачном рестарте. В `awg0.conf` перезаписываются
  `S1-S4` и `H1-H4`, добавляются/удаляются `HeaderProtectionKey`, `RandomTrailers` и
  серверный `ContentPaddingAddition`; HPK генерируется заново при каждом переходе на 3.1.
- `3.1 → X`: `S1`/`S2` остаются равными значениями из 3.1 — они валидны для всех уровней
  (равные значения не нарушают `S1+56 ≠ S2`, диапазон 15–32 ⊂ 15–150), меньше изменений
  для клиентов; перегенерируются только `S3/S4` (для 2.0) и `H1-H4`, поля 3.x удаляются.
- `1.0 ↔ 1.5` остаётся metadata-only; `3.1 ↔ 1.5` — НЕ metadata-only (серверные поля
  разные), полный путь с рестартом.
- Предохранители при переходе на 3.1:
  - установленная версия движка проверяется до перезаписи файлов: коммит `amneziawg-go`
    из `$DIR/versions` должен совпадать с `upstream.lock` (equality, как в `update.sh`);
    иначе отказ с подсказкой `update.sh`. При `install.sh --bin-dir` без файла `versions` —
    предупреждение (движок не подтверждён), не отказ;
  - если задан явный `$DIR/client-mtu` больше 1320 — предупреждение о фрагментации
    (паддинг + трейлеры); молча не переопределяем. `awg-client mtu` без аргумента
    показывает дефолт с учётом протокола.
- Сообщение после переключения: все клиенты должны перекачать конфиги (текст уже есть) +
  строка про MTU 1280 по умолчанию и про то, что все клиенты (включая контейнерные мосты)
  должны понимать 3.1.

## Совместимость с AmneziaWG-to-Proxy

Проверено по `D:\MyProjects\AmneziaWG-to-Proxy` (2026-11-11):

- Контейнер собирается на запиненном образе `ghcr.io/mainfrezzer/amnezia-bridge`
  (digest `fcfa9ae5…`); `amneziawg-go`/`awg`/`awg-quick` — из базового образа, оверлей
  пакетов их не обновляет.
- Собственного парсинга полей AWG у контейнера нет: конфиги применяются как есть, из
  проверок — только `AllowedIPs = 0.0.0.0/0` (split tunnel не поддержан).
- Документация контейнера (`docs/CONFIGURATION.md`) подтверждает 1.0/1.5/2.0 (реальные
  handshake-тесты между двумя контейнерами); про 3.x — ничего. Движок образа 3.1-ключи
  (`HeaderProtectionKey` и др.) не знает: ожидаемо `awg-quick up` падает → strike →
  карантин в `bad_config`.

Вывод и правило: сервер, обслуживающий AmneziaWG-to-Proxy, **не переводится на 3.1**,
пока образ контейнера не получит 3.1-движок (отдельная работа в том проекте: новый
digest базового образа или подкладка своих бинарников; фейл-тест `awg-quick up` с
3.1-конфигом там же). Наша сторона: README кита отмечает несовместимость, сообщение
`awg-client protocol 3.1` напоминает про контейнерные мосты. Кит контейнер не
детектирует и не блокирует — правило операционное, не кодовое.

## Генераторы и валидация

- `lib/common.sh`: `awg_h_values` получает ветку 3.1 → `1/2/3/4`; новая
  `awg_s31_value` — одно случайное 15–32; `awg_s34_values` (2.0) не трогается.
- `install.sh`: `--protocol 1.0|1.5|2.0|3.1`, меню получает 4-й пункт (Enter = 1.0),
  HPK-генерация, новые строки в `awg0.conf`; `VERSION` → 1.4.0.
- `awg-client protocol 3.1`/`3.0`: `3.1` принят, `3.0` и прочие отвергаются сообщением
  «supported: 1.0, 1.5, 2.0, 3.1».
- `awg-client version` показывает 3.1 как остальные уровни.

## Тесты

- `tests/test-install.sh`: цикл по 3.1 (поля сервера и клиента, равные `S ≥ 12`,
  `H = 1-4`, HPK совпадает с серверным, таймеры/паддинг в клиентском конфиге, MTU 1280,
  `3.0` отвергнут с новым сообщением); диапазоны новых генераторов в блоке lib.
- `tests/test-reliability.sh` (кейс `protocol`): `2.0 → 3.1` с фейковым systemctl
  (замена полей, бэкапы, рестарт), откат при неудачном рестарте, `3.1 → 2.0` удаляет
  поля 3.x и сохраняет равные `S1/S2`, кастомные `ContentPaddingAddition`/таймеры
  переживают переходы; отказ включить 3.1 при неподходящем `$DIR/versions` и
  предупреждение при явном `client-mtu > 1320`.
- Живая VM по `docs/testing/reliability-vm.md`: подъём с реальным amneziawg-go 3.1
  (нет `EINVAL`), `awg show`. Реальный клиент (Amnezia VPN ≥ 5.0.1.5 / AmneziaWG ≥ 3.1)
  — вручную после выката, в STATUS отдельно.

## Не-цели и анти-цели

Уровень 3.0; kmod; IPv6; рандомизация `Jc/Jmin/Jmax`; вариант `RandomTrailers = off`;
персональная рандомизация sender-полей per-client; смена `upstream.lock`.
Анти-цель: сломать существующие 1.0/1.5/2.0-серверы или сменить их протокол молча.

## Риски

- Старые клиенты не поднимут конфиг 3.1 → уровень opt-in, минимальные версии в справке
  и README, переключение само предупреждает о перекачке конфигов.
- AmneziaWG-to-Proxy (движок ≤2.0 в образе) не примет 3.1-конфиг, а сервер на 3.1
  «отвалит» его текущий ≤2.0-конфиг (HPK/RandomTrailers обязаны совпадать) → правило
  «не переключать такие серверы» в README и в сообщении переключения; обновление образа
  контейнера — отдельная работа в том проекте.
- Старый движок на сервере уронит туннель на неизвестных ключах UAPI → проверка
  `versions` до перехода на 3.1 (см. предохранители).
- `S < 12` → `EINVAL`, туннель не поднимется → генератор от 15, тест на диапазон.
- Фрагментация из-за трейлеров/паддинга → клиентский MTU 1280 по умолчанию для 3.1,
  предупреждение при явном MTU > 1320.
- Секретность HPK → только в `awg0.conf` (600) и клиентских конфигах (600); в логах и
  `list`/`version` не печатается.
